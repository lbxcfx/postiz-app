#### D. ⚠️ 双路径问题（极其重要）

本项目在开发环境中存在 **两份代码副本**，必须注意区分：

| 路径 | WSL 内路径 | 用途 |
|------|-----------|------|
| Windows `f:\postiz-app` | `/mnt/f/postiz-app` | IDE 编辑（VS Code 打开的目录） |
| WSL Home `~/postiz-app` | `/home/lbx/postiz-app` | **开发服务器实际运行目录** |

> 🚨 **关键**：开发服务器（`pnpm run dev`）运行在 WSL Home 路径 `~/postiz-app`，而非 Windows 挂载路径 `/mnt/f/postiz-app`。通过 IDE（VS Code）编辑的文件默认写入 Windows 路径，**不会自动同步到 WSL Home 路径**！

**常见症状**：
- 修改了代码但刷新页面没有任何效果
- 新增的翻译 key 不生效
- Console.log 调试代码不输出

**解决方案**：编辑文件后需手动同步到 WSL Home 目录，或直接在 WSL 终端内编辑：

```bash
# 同步单个文件（示例）
cp /mnt/f/postiz-app/path/to/file ~/postiz-app/path/to/file

# 批量同步所有修改过的文件（推荐）
rsync -av --exclude='node_modules' --exclude='.next' --exclude='.git' \
  /mnt/f/postiz-app/ ~/postiz-app/

# 同步后需重启前端服务
fuser -k -9 4200/tcp 2>/dev/null
sleep 2
cd ~/postiz-app/apps/frontend && rm -rf .next && pnpm run dev
```

> 💡 **建议**：可考虑在 WSL Home 中创建软链接，或将 VS Code 的工作目录改为通过 `Remote - WSL` 扩展直接打开 `~/postiz-app`，从而避免双路径问题。

## 4. 总体架构（V1）

### 4.1 架构原则

1. **编排执行分离**：`orchestrator` 只做 Workflow/Activity 编排。
2. **单一写链路**：业务数据只由 `backend` 写入 Postgres（Prisma）。
3. **复用优先**：优先使用已有的 `MaterialsModule`、`XiaohongshuProvider`、`PostActivity`，不重复建设。
4. **幂等优先**：请求幂等、发布幂等、任务可重试可补偿。
5. **人工兜底**：所有自动发布失败均可转人工处理。

### 4.2 服务边界与调用关系

```
┌─────────────┐     ┌──────────────┐     ┌──────────────────┐
│  Frontend   │────▶│   Backend    │────▶│  Orchestrator    │
│  (Next.js)  │◀────│   (NestJS)   │◀────│  (Temporal)      │
│  port:4200  │ SSE │  port:3000   │     │  port:7233       │
└─────────────┘     └──────┬───────┘     └────────┬─────────┘
                           │                      │
              ┌────────────┼──────────────────────┤
              ▼            ▼                      ▼
    ┌──────────────┐ ┌──────────┐     ┌───────────────────┐
    │ MediaCrawler │ │ Postgres │     │ social-auto-upload│
    │ (FastAPI)    │ │  + Redis │     │  (Playwright)     │
    │ port:8081    │ │          │     │  port:5409        │
    └──────────────┘ └──────────┘     └───────────────────┘
```

- **`apps/backend`**
  - 对前端提供 API（REST + SSE）。
  - 管理任务、草稿、发布、审计。
  - 通过 `MaterialsModule` 调用 MediaCrawler。
  - 通过 Temporal Client 启动/查询工作流。

## 6. 核心工作流（V1）— ContentFactoryWorkflow

### 6.1 状态机

```
CREATED ──▶ COLLECTING ──▶ UNDERSTANDING ──▶ GENERATING ──▶ REVIEWING ──▶ PUBLISHING ──▶ COMPLETED
   │            │                │                │             │              │
   └────────────┴────────────────┴────────────────┴─────────────┴──────────────┘
                                      ▼
                                   FAILED
                          (支持重试或人工接管)
```

### 6.2 Temporal Workflow 设计

```typescript
// apps/orchestrator/src/workflows/content-factory.workflow.ts（新建）
export async function contentFactoryWorkflow(input: ContentFactoryInput) {
  // Stage 1: 采集
  const sourceContent = await collectContent(input.collectParams);
  
  // Stage 2: 理解（仅视频类需要）
  let analysisResult = null;
  if (sourceContent.hasVideo) {
    analysisResult = await analyzeContent(sourceContent);
  }
  
  // Stage 3: 生成
  const draft = await generateDraft({
    sourceContent,
    analysisResult,
    productProfile: input.productProfile,
  });
  
  // Stage 4: 审核（人工介入点 - 使用 Temporal Signal 等待）
  const reviewResult = await condition(() => reviewSignalReceived);
  if (reviewResult === 'reject') {
    // 重生逻辑
    return contentFactoryWorkflow({ ...input, retry: true });
  }
  
  // Stage 5: 发布
  const publishResult = await publishContent({
    draft,
    accountId: input.accountId,
    scheduleAt: input.scheduleAt,
  });
  
  return publishResult;
}
```

### 6.3 Activity 映射

| Activity | 模块 | 依赖 | 状态 |
|----------|------|------|------|
| `collectContent` | `MaterialsQueueService` | MediaCrawler | ✅ 已有基础 |
| `analyzeContent` | `AnalysisService` 已接入 | Qwen VL API | ✅ 已开发（含降级） |
| `generateDraft` | `ContentFactoryActivity.generateDraft` | Qwen API | ✅ 已开发 |
| `reviewContent` | Temporal Signal/Query | 人工操作 | ✅ 已开发 |
| `publishContent` | 复用 `PostActivity.postSocial` | XiaohongshuProvider | ✅ 已有 |

### 6.4 重试与补偿

- **Activity 重试**：指数退避（已有模式参考 `autopost.workflow.ts`）
  ```typescript
  retry: {
    maximumAttempts: 3,
    backoffCoefficient: 2,
    initialInterval: '30 seconds',
  }
  ```
- **发布补偿**：失败进入 `publish_retry_queue`，超过阈值转人工。
- **幂等键**：
  - 采集：`platform + queryHash`（已有 `MaterialsService.buildQueryHash`）
  - 发布：`account_id + content_hash + schedule_at`

| Prisma 迁移破坏现有表 | 数据丢失 | 低 | 仅 additive migration，测试环境先行 |
| Temporal 工作流版本冲突 | 运行中工作流中断 | 低 | 使用 Temporal versioning API |
