# 开发环境启动方案 (WSL)

本文档描述了将开发环境迁移至 WSL 原生目录后的标准启动流程。

## 1. 核心变更说明

### 2026-02-13
由于 Windows 挂载盘 (/mnt/f) 的 I/O 性能问题严重影响后端编译与运行，全栈开发环境已迁至 WSL 原生目录 `~/postiz-app`。

### 2026-02-15
解决了通过 Windows PowerShell 调用 `wsl -e` 启动服务时，`nohup` 后台进程收到 SIGHUP 被终止的问题。
**根因**：`wsl -e` 命令退出后，其创建的终端会话关闭，导致所有通过 `nohup` 启动的子进程收到 SIGHUP 信号而退出。
**方案**：使用 `setsid` 创建独立会话组，使后台进程完全脱离 WSL 终端的生命周期。

### 2026-02-17
将 `PostgreSQL + Redis + Temporal` 统一切换为 WSL 本地服务（无 Docker 依赖）。
**当前主方案**：本地 `PostgreSQL + Redis + Temporal`（完整链路，默认无 Docker）。

### 2026-02-17（补充）
启动链路已加入 Prisma 自动同步，避免注册/登录时报错 `The table public.User does not exist`：
- `scripts/wsl/start-dev.sh` 在启动应用前自动执行 `pnpm run prisma-db-push`
- `run.sh` / `run.ps1` 也已加入 `pnpm run prisma-db-push`

### 2026-02-17（素材库登录链路修复）
修复素材库“小红书已登录误判 + 点击未登录无二维码 + 搜索无结果”问题：
- `MediaCrawler/api/services/login_checker.py`：
  - 登录判定从“命中任意 cookie”改为“必须命中全部必需 cookie”
  - 新增 cookie 时效校验（默认 24 小时，`LOGIN_STATE_MAX_AGE_HOURS` 可配置）
- `libraries/nestjs-libraries/src/materials/materials.queue.service.ts`：
  - 二维码提取兼容 `QRCODE_BASE64:` 与 `BROWSER_SCREENSHOT_BASE64:` 两种日志标记
- 运行态处理：
  - 清理过期小红书 cookie 文件后，`/api/crawler/login-status/xhs` 应返回 `has_valid_login=false`
  - 清理卡住的 `bull:materials:active` 任务，避免搜索任务长期无结果

## 2. 启动流程 (主方案)

每次开发前，请严格按照以下步骤操作：

### 方式一：从 Windows PowerShell 一键启动 (主方案，无 Docker)

在 Windows PowerShell 中直接运行以下**单条命令**，无需手动进入 WSL：

```powershell
wsl -d Ubuntu -- bash -c "fuser -k 3000/tcp 4200/tcp 8081/tcp 7233/tcp 8080/tcp 2>/dev/null; cd ~/postiz-app && export USE_LOCAL_POSTGRES_REDIS=1 && export USE_LOCAL_TEMPORAL=1 && export FORCE_WSL_DEV=1 && export NODE_OPTIONS=--max-old-space-size=3072 && setsid ./scripts/wsl/start-dev.sh < /dev/null > /dev/null 2>&1 && sleep 60 && echo '=== BACKEND ===' && tail -5 .runtime/logs/backend.log && echo '=== FRONTEND ===' && tail -5 .runtime/logs/frontend.log && echo '=== MEDIACRAWLER ===' && tail -5 .runtime/logs/mediacrawler.log && echo '=== TEMPORAL ===' && tail -5 .runtime/logs/temporal.log && echo '✅ Services Started! DO NOT CLOSE THIS WINDOW' && tail -f /dev/null"
```

**命令说明**：
- `fuser -k 3000/tcp 4200/tcp 8081/tcp 7233/tcp 8080/tcp` — 启动前自动清理残留端口占用
- `wsl -d Ubuntu -- bash -c "..."` — 在指定的 Ubuntu 发行版中执行命令
- `export USE_LOCAL_POSTGRES_REDIS=1` — 使用 WSL 本地 Postgres/Redis（推荐默认）
- `export USE_LOCAL_TEMPORAL=1` — 使用 WSL 本地 Temporal Dev Server（推荐默认）
- `export FORCE_WSL_DEV=1` — 强制使用 `pnpm dev` 模式启动后端/orchestrator
- `export NODE_OPTIONS=--max-old-space-size=3072` — 防止内存溢出 (由 4GB 调降至 3GB)
- `setsid ./scripts/wsl/start-dev.sh < /dev/null > /dev/null 2>&1` — **关键**：通过 `setsid` 在新会话中启动，避免 SIGHUP 终止进程
- `sleep 60` — 等待 60 秒让服务完成编译和启动
- `tail -5 .runtime/logs/*.log` — 输出各服务日志尾部，用于确认启动状态

如需切回 Docker Temporal（不推荐），可设置 `USE_LOCAL_TEMPORAL=0`。

### 方式二：从 WSL 终端手动启动

如果你已经在 WSL Shell 中（如通过 Windows Terminal 打开 Ubuntu 标签页），可手动分步执行：

#### 步骤 1：进入原生目录 (关键)
必须在 Linux 用户目录下运行，严禁在 `/mnt/f` 下运行。
```bash
cd ~/postiz-app
```

#### 步骤 2：准备环境
确保 Node.js 版本正确 (后端要求 v22+)。
```bash
source ~/.nvm/nvm.sh
nvm use 22
# 如未安装: nvm install 22 && nvm alias default 22
```

首次使用本地数据服务时先执行：
```bash
./scripts/wsl/setup-local-postgres-redis.sh
./scripts/wsl/setup-local-temporal.sh
```

#### 步骤 3：启动服务
```bash
# 本地 Postgres/Redis 模式（默认推荐）
export USE_LOCAL_POSTGRES_REDIS=1
export USE_LOCAL_TEMPORAL=1

# 强制开发模式 + 内存优化
export FORCE_WSL_DEV=1
export NODE_OPTIONS=--max-old-space-size=4096

# 启动 (在 WSL 原生终端中可直接运行，无需 setsid)
./scripts/wsl/start-dev.sh
```

说明：`start-dev.sh` 会在应用启动前自动执行一次 `pnpm run prisma-db-push`，保证数据库表结构与 Prisma schema 同步。

> ⚠️ **注意**：在 WSL 原生终端（如 Windows Terminal 的 Ubuntu 标签页）中启动时，**不要关闭该终端窗口**，否则后台进程仍会被终止。如果需要关闭终端，请改用方式一的 `setsid` 方式。

## 3. 验证服务

启动后等待约 **60 秒**（后端编译约 30s，前端编译约 6s），然后验证：

### 方式一：HTTP 状态检查
```bash
# 在 WSL 中运行
curl -s -o /dev/null -w '%{http_code}' http://localhost:3000/docs; echo ' Backend'
curl -s -o /dev/null -w '%{http_code}' http://localhost:4200; echo ' Frontend'
curl -s -o /dev/null -w '%{http_code}' http://localhost:8081/docs; echo ' MediaCrawler'
```

预期输出：
```
200 Backend
307 Frontend    # 307 是重定向到登录页，属于正常
200 MediaCrawler
```

### 方式二：浏览器访问
| 服务 | 地址 | 预期状态 |
|------|------|----------|
| Backend API | http://localhost:3000/docs | Swagger 文档页面 |
| Frontend | http://localhost:4200 | 登录/首页 |
| MediaCrawler | http://localhost:8081/docs | FastAPI 文档页面 |
| Temporal UI | http://localhost:8080 | Temporal 控制台 |

### 方式三：健康检查脚本（主方案）
```bash
USE_LOCAL_POSTGRES_REDIS=1 SKIP_TEMPORAL_CHECK=0 ./scripts/wsl/health-check.sh
```

### 方式四：查看日志确认启动
```bash
# 在 WSL 中运行
tail -20 ~/postiz-app/.runtime/logs/backend.log
tail -20 ~/postiz-app/.runtime/logs/frontend.log
tail -20 ~/postiz-app/.runtime/logs/mediacrawler.log
tail -20 ~/postiz-app/.runtime/logs/orchestrator.log
tail -20 ~/postiz-app/.runtime/logs/temporal.log
```

**后端启动成功标志**：日志中出现 `localhost:3000 started +xxxms`
**前端启动成功标志**：日志中出现 `✓ Ready in x.xs`
**MediaCrawler 启动成功标志**：日志中出现 `Application startup complete`

## 4. 停止服务

```bash
# 主方案：停止本地服务（包含本地 Temporal）
wsl -- bash -c "cd ~/postiz-app && USE_LOCAL_TEMPORAL=1 ./scripts/wsl/stop-dev.sh"

# 兼容模式：如启用 Docker Temporal，可额外停止 Docker 基础设施
wsl -- bash -c "cd ~/postiz-app && USE_LOCAL_TEMPORAL=0 STOP_DOCKER_INFRA=1 ./scripts/wsl/stop-dev.sh"
```

## 5. 服务架构概览

`start-dev.sh` 脚本会启动以下 5 个应用服务 + 基础设施：

| 服务 | 启动方式 | 端口 | 说明 |
|------|----------|------|------|
| backend | `pnpm --filter ./apps/backend run dev` | 3000 | NestJS 后端 API |
| orchestrator | `pnpm --filter ./apps/orchestrator run dev` | — | Temporal Worker |
| frontend | `pnpm --filter ./apps/frontend run dev` | 4200 | Next.js 前端 |
| social_auto_upload | `uv run python3 sau_backend.py` | — | 社交平台自动发布 |
| mediacrawler | `uvicorn api.main:app --port 8081` | 8081 | 小红书爬虫 API |

基础设施：
- 主方案：本地服务 `PostgreSQL(5432)`、`Redis(6379)`、`Temporal(7233)`、`Temporal UI(8080)`
- 可选兼容模式：设置 `USE_LOCAL_TEMPORAL=0` 使用 Docker Temporal

## 6. 常见问题排查

- **Q: 从 PowerShell 启动后进程立即退出（日志为空）**
  - A: 这是 `wsl -e` 的 SIGHUP 问题。**必须使用 `setsid`** 包裹 `start-dev.sh`。参见方式一的启动命令。

- **Q: 启动后后端无响应 (Connection Refused)**
  - A: ①检查是否忘记切换目录（仍在 `/mnt/f`）；②检查 Node 版本是否 < v22（`node -v` 确认）；③等待时间不够（后端编译需 ~30s）。

- **Q: 编译过程内存溢出 (OOM)**
  - A: 确保已导出 `NODE_OPTIONS=--max-old-space-size=4096`。

- **Q: MediaCrawler 报 `[Errno 98] Address already in use`**
  - A: 端口 8081 被之前的进程占用。清理方法：
    ```bash
    wsl -- bash -c "lsof -ti:8081 | xargs kill -9 2>/dev/null; echo done"
    ```

- **Q: 脚本权限拒绝**
  - A: 运行 `chmod +x scripts/wsl/*.sh` 修复权限。

- **Q: 启动脚本提示 `[SKIP] xxx already running`，但服务实际不可用**
  - A: PID 文件残留导致。清理后重启：
    ```bash
    wsl -- bash -c "rm -f ~/postiz-app/.runtime/pids/*.pid"
    ```
    然后重新执行启动命令。

- **Q: Backend 日志出现 `Configuration issues found: 1`**
  - A: 这是配置警告，不影响正常运行。通常是某个可选配置（如第三方 OAuth）未设置。

- **Q: 注册/登录报错 `The table public.User does not exist in the current database`**
  - A: 当前连接的数据库尚未同步 Prisma schema。执行：
    ```bash
    cd ~/postiz-app
    pnpm run prisma-db-push
    ```
  - 然后重启服务，再访问登录/注册页面。

- **Q: 端口 `4200` 或 `3000` 显示被占用 (EADDRINUSE)**
  - A: 这是因为旧的进程未被彻底清理。
    - **解决方案**：使用 `lsof` 强制清理残留进程：
      ```bash
      wsl -- bash -c "lsof -ti:3000,4200,8081 | xargs -r kill -9"
      ```
    - 现在的“一键启动命令”已内置此逻辑。

- **Q: 启动失败提示 `Missing command: temporal`**
  - A: Temporal CLI 未安装。执行：
    ```bash
    ./scripts/wsl/setup-local-temporal.sh
    ```
  - 安装后重启：
    ```bash
    USE_LOCAL_TEMPORAL=1 USE_LOCAL_POSTGRES_REDIS=1 FORCE_WSL_DEV=1 ./scripts/wsl/start-dev.sh
    ```
- **Q: Frontend 访问一会儿后断开 (OOM)**
  - A: 日志中出现 `Out of memory: Killed process xxx`。
    - **原因**：WSL 分配的内存耗尽（Backend + Frontend + PyCrawler + Docker 全家桶）。
    - **解决方案**：
      1. 减少 Node.js 内存占用：启动命令中 `max-old-space-size` 已调降至 3072 (3GB)。
      2. 增加 Swap：在 Windows 用户目录下创建 `.wslconfig` 文件，增加 swap 大小。
      3. 关闭不必要的应用：确保 Docker Desktop 中没有运行其他无关容器。

- **Q: 浏览器打开 `http://localhost:4200` 还是打不开**
  - A: 先区分是“服务未启动”还是“浏览器/转发问题”：
    ```bash
    # Windows 侧检查
    curl -I http://localhost:4200/auth
    curl -I http://localhost:3000/docs
    ```
  - 如果两条都返回 `200`，说明服务正常，优先处理浏览器侧：
    1. 地址栏必须使用 `http://`（不要用 `https://`）。
    2. 直接访问 `http://localhost:4200/auth`。
    3. 关闭系统代理或将 `localhost,127.0.0.1` 加入代理例外。
  - 如果 `curl` 也失败，执行一次 WSL 网络与服务恢复：
    ```powershell
    wsl --shutdown
    wsl -d Ubuntu -- systemctl --user start postiz-temporal.service postiz-backend.service postiz-orchestrator.service postiz-frontend.service
    ```
    然后重试 `curl -I http://localhost:4200/auth`。
  - 若 `3000/8081` 可访问但 `4200` 仍不通，检查前端是否只监听 IPv6：
    ```bash
    wsl ss -ltnp4 | grep 4200
    ```
    如果没有输出，请将前端 dev 命令改为 `next dev -H 0.0.0.0 -p 4200` 并重启前端服务。

- **Q: `curl` 偶尔可用，但过一会儿又完全打不开（`wsl -l -v` 显示 `Ubuntu Stopped`）**
  - A: 这是 WSL 发行版退出导致服务整体下线。可使用系统级服务并保持一个会话存活：
    ```powershell
    wsl -d Ubuntu -u root -- bash -lc "systemctl start postiz-dev-temporal.service postiz-dev-backend.service postiz-dev-orchestrator.service postiz-dev-frontend.service postiz-dev-mediacrawler.service; tail -f /dev/null"
    ```
  - 说明：该命令会拉起系统级 dev 服务（包含 MediaCrawler 8081），并通过 `tail -f /dev/null` 保持会话不退出；请保持该窗口打开。
  - 推荐：直接双击仓库根目录 `run-keepalive.cmd`，会自动确保并启动 `postiz-dev-mediacrawler.service`。
  - 验证：
    ```powershell
    curl -I http://localhost:4200/auth
    curl -I http://localhost:3000/docs
    curl -I http://localhost:8081/docs
    ```

- **Q: 素材库页面显示“已登录”，但点击登录无弹窗，搜索也无结果**
  - A: 这是旧登录判定与二维码事件解析不兼容引起的组合问题。按下面步骤恢复：
    1. 确认已部署最新 `login_checker.py` 与 `materials.queue.service.ts`（见上方 2026-02-17 补充）。
    2. 清理旧 cookie：
       ```bash
       rm -f ~/postiz-app/MediaCrawler/browser_data/cdp_xhs_user_data_dir/Default/Network/Cookies*
       rm -f ~/postiz-app/MediaCrawler/browser_data/xhs_user_data_dir/Default/Network/Cookies*
       ```
    3. 重启服务：
       ```bash
       sudo systemctl restart postiz-dev-mediacrawler.service
       sudo systemctl restart postiz-dev-backend.service
       ```
    4. 验证登录状态接口：
       ```bash
       curl -s http://127.0.0.1:8081/api/crawler/login-status/xhs
       ```
       预期 `has_valid_login=false`，前端显示“未登录(点击登录)”，点击后应出现二维码弹窗。

- **Q: 素材库点击登录后一直“登录处理中”，没有弹出二维码**
  - A: 常见根因是 WSL 无可用 X Server，而后端尝试以 headed 模式拉起 Playwright，报错 `Missing X server or $DISPLAY`。
  - 当前默认策略已改为：未显式开启时使用 headless（二维码通过前端弹窗展示），避免依赖本地 GUI。
  - 如确需 headed 模式，可显式设置环境变量：
    ```bash
    export MATERIALS_ALLOW_HEADED_BROWSER=1
    ```
    并确保系统存在可用 X Server。

- **Q: 扫码后无反应，是否可以直接手机号+验证码登录（不依赖弹窗）**
  - A: 已支持。使用素材库页右上角“手机号登录”流程：
    1. 输入手机号，点击“手机号登录”（后端会以 `loginType=phone` 启动登录任务）。
    2. 收到短信后，在同一区域输入验证码并点击“提交验证码”。
    3. 后端将验证码转发到 MediaCrawler `/api/crawler/sms-code`，登录成功后状态会自动刷新为“已登录”。
  - 若一直停留在“登录处理中”，请先确认：
    ```bash
    curl -s http://127.0.0.1:8081/docs > /dev/null && echo mediacrawler_ok
    curl -s http://127.0.0.1:3000/materials/login-status?platform=xhs
    ```
